# Product

## Problem

Developers rarely update their portfolio: it is tedious manual work, even though all the information already lives on GitHub. The site quickly goes stale.

## Solution

The service reads a GitHub profile and public repositories, builds a portfolio site from a template, and then **keeps it up to date on its own**. What GitHub does not have (about me, contacts, social links, certificates) the user adds themselves.

## Audience

Developers who need a public portfolio page (job search, freelancing, personal brand) without writing and maintaining their own site.

## Project goals

1. A working SaaS product.
2. **Learning.** The owner understands every technical and architectural decision in depth. Development follows the explain-first workflow in `CLAUDE.md`, and each milestone ends with learning notes (`docs/learning/`).

## Key principles

- **Automatic, but under control.** Every change to the site is a PR with a preview. Auto-merge is an option, off by default.
- **The data belongs to the user.** Content and images live in their repository; we host, but the data is portable.
- **A manual edit beats generation.** What the user edited, the agent never touches again.
- **Texts sound human.** Users publish descriptions and posts under their own name, so the style is restrained and concrete, without marketing clichés or emojis by default.

## User flows

### 1. Onboarding
1. Sign in with GitHub.
2. The service creates (or the user picks) a portfolio data repository and installs the GitHub App on it.
3. The service reads the profile and public repos and suggests a project list; the user marks which to show (`portfolio` topic or a checkbox in the dashboard; see `architecture.md`, open questions).
4. The user picks a template and fills in about me, contacts, social links.
5. First PR → preview → published at `username.<domain>`.

### 2. New project
1. The user makes a repo public and adds the `portfolio` topic.
2. The pipeline generates a project card and a post draft.
3. A PR with a preview is opened; the user gets the link.
4. Merge manually or automatically (if enabled and all checks pass) → production.

### 3. Project update
- README change → the card is updated (except fields in `editedFields`).
- New GitHub Release → card update + a "what's new" post draft.
- Regular pushes without a README change do not generate posts.

### 4. Inline editing
1. On their site the user adds `?edit` → redirect to the app's editor.
2. The editor shows the same template with editable fields (`contenteditable`) and image replace buttons.
3. Changes are visible immediately. "Save" → PR → preview link. "Publish" → merge.

### 5. Social posts
- Drafts are generated by the pipeline (new project, release) and live in the dashboard.
- The Chrome extension shows drafts in a Side Panel on any site: copy, edit, mark as published. Autofill into the LinkedIn composer is a later version.
- The user always presses "publish" themselves.

### 6. Chat agent
The user describes a change in words ("make project X's description shorter", "use a dark theme"). The agent changes the portfolio data → PR with a preview.

### 7. Custom domain
The user adds a domain and sets up a CNAME; the service issues SSL and serves the site on it.

## Out of MVP scope
Auto-posting through social network APIs, autofill into social network composers, export to GitHub Pages, visit analytics, monetization.
