# Архітектура

## Огляд

Три тригери (GitHub, inline-редактор, чат-агент) зводяться до однієї дії: **змінити дані портфоліо в репо користувача через PR**. Далі завжди однаково: збірка → прев'ю → merge → продакшн.

```
GitHub події ─┐
Редактор ─────┼─► Hono API / черга ─► зміна даних ─► PR ─► збірка Astro ─► R2 (прев'ю) ─► merge ─► R2 (прод)
Чат-агент ────┘                     └─► чернетки постів (D1) ─► дашборд / Chrome extension
```

## Компоненти

| Компонент | Пакет | Рантайм | Відповідальність |
|---|---|---|---|
| Шаблони | `packages/templates` | Astro | Рендер сайту з даних. Кожен редагований елемент має `data-field` (див. `data-model.md`). |
| Core | `packages/core` | будь-який | Zod-схеми, GitHub-клієнт, LLM-шар, санітизація, генератори картки й поста. |
| App | `apps/app` | Cloudflare Workers | Astro SSR (дашборд, редактор), Hono API, обробка вебхуків, споживач черги. |
| Site server | `apps/site-server` | Cloudflare Workers | Мультитенантна роздача сайтів з R2 за hostname. |
| Білд-раннер | див. відкриті питання | — | `astro build` даних конкретного користувача, завантаження результату в R2. |
| Extension | `apps/extension` | Chrome MV3 | Side Panel з чернетками постів. |

Інфраструктура Cloudflare: Workers, Queues (задачі генерації і збірки), D1 (користувачі, налаштування, чернетки постів, стан задач), R2 (зібрані сайти), Cloudflare for SaaS (власні домени), Cron Triggers.

## Хостинг сайтів (ADR 0001)

- Один Worker `site-server` обслуговує всі сайти. За `Host` знаходить користувача (D1, з кешем у KV) і віддає файли з R2.
- Розкладка R2:
  - `sites/<userId>/prod/…` — продакшн.
  - `sites/<userId>/preview/<prNumber>/…` — прев'ю PR.
- Адреси: прод `username.<домен>`; прев'ю `pr-<n>--username.preview.<домен>` (wildcard DNS на власній зоні); власні домени через custom hostnames Cloudflare for SaaS.
- Відповіді кешуються через Cache API; після деплою кеш користувача інвалідується.
- Окремий проєкт Cloudflare Pages на кожного користувача **не** створюємо: акаунт має soft limit на кількість проєктів і обмеження на збірки.

## Пайплайн "новий / оновлений проєкт"

1. **Виявлення події** (див. відкриті питання щодо механізму). Цікаві події: репо став публічним, з'явився topic `portfolio`, змінився README, новий Release.
2. **Збір даних** (`core/github`): README, `/languages`, topics, homepage, stars, дата останнього push, скріншоти з репо, release notes (для релізу).
3. **Генерація** (`core/llm`): картка проєкту і, якщо подія того варта, чернетка поста. Модель повертає JSON через tool use.
4. **Валідація**: Zod-схема з `data-model.md`. Невалідно → один retry з помилкою валідації в промпті → невалідно знову → задача `failed`, користувач бачить помилку в дашборді.
5. **Злиття з існуючими даними**: поля з `editedFields` беремо з поточного файлу, не з генерації.
6. **PR** у репо даних: гілка `portfolio-bot/<slug>-<timestamp>`, один файл проєкту + асети. Опис PR — людською мовою, що змінилося.
7. **Збірка й прев'ю**: білд-раннер збирає сайт з гілки PR і кладе в `preview/<prNumber>`. Посилання — коментарем у PR і в дашборді.
8. **Merge**: вручну або auto-merge, якщо увімкнено і всі перевірки (схема, збірка) зелені. Після merge — збірка в `prod`.

Пости зберігаються в D1 як чернетки з посиланням на проєкт і подію; у репо не потрапляють.

## LLM (ADR 0003)

- Провайдер: Anthropic. Весь доступ — через інтерфейс у `core/llm` (одна функція на задачу: `generateProjectCard`, `generatePost`, `chatEdit`), щоб заміна провайдера була зміною реалізації, а не викликів.
- Моделі в конфігурації, не в коді: дешева модель рівня Haiku — картки й пости; Sonnet — чат-агент. Ідентифікатори моделей звір з актуальною документацією Anthropic перед першим використанням.
- Системні промпти й інструкції стилю — стабільний префікс, кешується (prompt caching).
- Ліміти генерацій на користувача на день зберігаються в D1; перевищення → задача відкладається.
- Безпека: вміст репо подається в промпт як дані в явно розмежованому блоці; модель на кроці генерації не має інструментів із записом; вивід проходить валідацію і санітизацію.

## Inline-редактор

- Живе в `apps/app` (`/edit`), не на публічному сайті. `?edit` на сайті користувача робить лише редирект.
- Рендерить ті самі компоненти `packages/templates` з прапором `editable`: елементи з `data-field` отримують `contenteditable`, зображення — кнопку заміни.
- Вставка в `contenteditable` чиститься до plain text.
- Зберегти: клієнт надсилає diff `{field: value}` → API застосовує до даних, додає поле до `editedFields` → коміт у гілку → PR → прев'ю.
- Зображення: завантаження → ресайз до ≤2000px і стиснення у WebP → коміт у `assets/` репо даних.

## Chrome extension

- MV3, Side Panel API. Авторизація — токеном сесії застосунку (логін через сторінку застосунку).
- v1: список чернеток, копіювати, редагувати, "опубліковано". Жодної взаємодії з DOM соцмереж.

## Відкриті питання

1. **Білд-раннер.** Workers не запускають `astro build`. Варіанти: GitHub Actions у службовому репо (запуск через `workflow_dispatch` з API); Cloudflare Containers; власна збірка без Astro CLI. Потрібне рішення до M3 → ADR.
2. **Виявлення подій і права GitHub App.** Вебхуки приходять лише з репо, на які встановлено App, а права App однакові для всіх цих репо. Встановлення на всі репо з `contents: write` — надмірні права. Рекомендований варіант: App встановлено **лише на репо даних** (запис), а публічні репо користувача опитуються Cron Trigger через API (публічні дані, затримка в хвилини). Альтернатива: вебхуки з усіх репо при правах лише на читання + окремий механізм запису. Потрібне рішення до M4 → ADR.
3. **Вибір проєктів для показу:** лише topic `portfolio`, лише галочка в дашборді, чи обидва (topic як автоматичний спосіб, галочка як ручний).
4. **Створення репо даних:** сервіс створює його від імені користувача (потрібен user token з відповідними правами) чи користувач створює з template-репо і обирає при встановленні App.
